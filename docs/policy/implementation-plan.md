## 2. 1차 UI 구현 범위

### 포함

- 나이, 지역, 구·군, 취업 상태, 소득 조건, 정책 분야 입력 UI
- 필수값 검증과 개인정보 안내
- 조건 입력 → 정책 목록 → 정책 상세 → 공식 페이지 이동 확인 흐름
- MockData를 사용한 조건별 결과, 빈 결과, 정렬 상태
- 마감일과 지원금이 없는 경우의 대체 문구
- 기존 관심 없음 처리와 실행 취소 동작 유지
- 좁은 화면에서의 텍스트 잘림과 overflow 검증

### 제외

- Spring Boot API 호출
- 사용자 조건 서버 저장
- 로컬 DB와 상태 관리 라이브러리 도입

## 5. 권장 모델

### PolicyFilterCondition

공통 정책 데이터 계약을 한곳에서 확인할 수 있도록 `lib/data/models.dart`에 다음 값을 정의한다.

```text
age
region
district
employmentStatus
incomeRange
category
```

구현 원칙:

- 나이는 `int`로 보관한다.
- 지역과 구·군은 화면 표시 문자열과 내부 식별값을 분리할 수 있게 작성한다.
- 취업 상태, 소득 구간, 정책 분야는 enum과 한국어 label extension 사용을 권장한다.
- `PolicyListPage`에는 개별 문자열 여러 개가 아니라 `PolicyFilterCondition` 하나를 전달한다.
- 실제 API 연동 전까지 조건은 메모리에만 유지한다.

### Policy 모델 보완

현재 필드를 유지하되 다음 후속 API 필드를 고려한다.

```text
id: String
supportAmount: int?
supportText: String
deadline: String?
officialUrl: String?
contact: String?
```

1차 작업에서 API 모델 전체를 미리 구현하지 않는다. 다만 지원금과 마감이 없을 수 있다는 전제는 UI에 반영한다.

## 9. 후속 백엔드 연동 시 교체 지점

백엔드 API가 준비되면 다음 순서로 교체한다.

1. [x] 백엔드 `PolicySummary`, `PolicyDetail`, 필터 코드 계약을 확인한다.
2. [x] MockData용 `Policy`와 분리된 API용 `PolicySummary`, `PolicyDetail` 모델을 추가한다.
3. [x] 정책 전용 API client를 추가한다.
4. [x] 정책 목록·상세·외부 확인 화면의 MockData 직접 참조를 API 결과로 교체한다.
5. [x] 로딩, 인증 실패, 외부 API 장애, 재시도, `partialResult` 상태를 추가한다.
6. [x] `CHECK_REQUIRED` 정책의 확인 안내와 사유를 목록·상세 화면에 표시한다.
7. [x] 실제 외부 링크 실행 범위를 정책 전용 외부 브라우저 연결로 확정한다.

API 연동 작업에서는 `API_BASE_URL` 설정을 사용하고 비밀값을 앱에 포함하지 않는다.

확정된 1차 백엔드 계약:

```text
POST /api/policies/search
  → ApiResponse<PolicySearchResponse>
  → items: PolicySummary[]
  → partialResult
  → checkedProviderPages

GET /api/policies/{policyId}
  → ApiResponse<PolicyDetail>
```

두 endpoint 모두 로그인 사용자의 액세스 토큰이 필요하다.
온통청년 인증키는 백엔드 서버에서만 관리하며 앱에는 포함하지 않는다.

## 13. 신청 링크와 참고 링크 역할 구분

### 선택한 방식

백엔드가 이미 `officialUrl`과 `referenceUrls`를 분리해 반환하므로 API 응답 계약은 변경하지 않는다.

정보를 확인하는 참고 경로로 표시한다. 참고 링크를 신청 링크로 자동 대체하지 않는다.

### 단계 1. 링크 상태 문구 보완

- [x] `officialUrl`이 없으면 “온라인 신청 링크 없음”을 표시한다.

- [x] 참고 링크가 실제 신청 경로임을 보장하지 않는다는 설명을 표시한다.

### 단계 2. 참고 링크 실행

- [x] 참고 URL을 문자열이 아닌 버튼으로 표시한다.
- [x] 신청 링크와 참고 링크가 같으면 참고 링크에서 중복 표시하지 않는다.
- [x] 참고 링크도 외부 이동 확인 화면과 URL 보안 검증을 거친다.
- [x] 확인 화면의 제목·설명·버튼 문구를 신청 링크와 참고 링크에 맞게 구분한다.

### 단계별 데이터 흐름

1. 정책 화면이 로그인 토큰으로 `GET /api/users/me/policy-preferences`를 호출한다.
2. `saved=false`이면 회원 나이만 자동 입력하고 나머지 조건 입력 화면을 표시한다.
3. `saved=true`이고 필수 조건이 유효하면 정책 탭 진입 시 저장 조건으로 목록을 자동 조회한다.
4. 사용자가 조건을 수정하고 저장을 선택하면 `PUT /api/users/me/policy-preferences`를 먼저 호출한다.
5. 저장 성공 후 동일한 조건으로 `POST /api/policies/search`를 호출한다.
6. 저장을 선택하지 않은 검색은 현재 화면에만 적용하고 서버의 기본 조건을 변경하지 않는다.

### 실패 처리

- 저장 조건 조회 실패: 입력 화면과 오류 안내를 함께 표시해 직접 검색은 계속할 수 있게 한다.
- 저장 실패: 저장된 것으로 오해하지 않도록 목록 조회로 넘어가지 않고 오류를 표시한다.
- 생년월일 없음: 저장된 나이를 임의로 만들지 않고 나이를 한 번 입력하도록 안내한다.
- 앱 지역 스냅샷과 저장 코드 불일치: 잘못된 이름을 표시하지 않고 지역을 다시 선택하도록 안내한다.
- 로그인 토큰 없음: 정책 조회와 계정 저장을 실행하지 않고 로그인 안내를 표시한다.

## 16. 디테일 2단계 — 전체 분야 탐색·더 보기·정책명 검색

### 적용한 판단

- 정책 분야가 `전체`이면 한 목록에 섞지 않고 주거·취업·자산형성·문화·교통 다섯 섹션으로 구분한다.
- 분야별 결과와 다음 페이지를 독립적으로 관리해 한 분야의 추가 조회가 다른 분야를 초기화하지 않게 한다.
- 한 번의 앱 요청은 백엔드와 온통청년의 같은 번호 페이지 한 장에 대응한다.
- 숫자 페이지를 건너뛰지 않고 백엔드가 반환한 `nextPage`만 사용해 필터링 과정의 정책 누락을 막는다.
- 검색어가 있거나 특정 분야를 선택한 경우에는 결과 의미가 하나이므로 단일 목록을 사용한다.
- 정책 검색은 백엔드가 제공처의 정책명 조건으로 전달하며 앞뒤 공백을 제거하고 최대 50자로 제한한다.

### 단계별 데이터 흐름

1. 분야가 전체이고 검색어가 없으면 앱이 다섯 분야에 대해 첫 페이지를 병렬 요청한다.
2. 백엔드는 각 요청의 `category`, `page`, `size`를 온통청년 형식으로 변환한다.
3. 백엔드는 제공처 한 페이지를 조건 판정·중복 제거한 뒤 `items`와 `nextPage`를 반환한다.
4. 앱은 분야별 섹션에 결과를 표시하고 `nextPage`가 있을 때만 해당 섹션의 `더 보기`를 표시한다.
5. 사용자가 `더 보기`를 누르면 그 분야와 `nextPage`만 요청하고 정책 ID가 같은 항목은 중복 추가하지 않는다.
6. 사용자가 정책명을 검색하면 검색어와 첫 페이지를 요청해 단일 목록으로 전환한다.
7. 검색어를 지우면 저장된 조건은 유지한 채 전체 분야 섹션을 다시 조회한다.

### 실패 처리

- 한 분야만 실패: 성공한 다른 분야는 유지하고 실패한 섹션 안에서만 재시도한다.
- 추가 조회 실패: 기존 정책은 유지하고 해당 분야의 추가 조회 상태만 해제한다.
- 오래 걸린 이전 검색 응답: 조회 세대 번호가 현재 요청과 다르면 화면 상태에 반영하지 않는다.
- 중복 정책: 분야별 추가 조회와 전체 분야 화면 모두 정책 ID를 기준으로 중복 표시하지 않는다.
- 필터 후 빈 페이지: 현재 항목이 0개여도 `nextPage`가 있으면 `더 보기`를 유지해 뒤 페이지를 놓치지 않는다.
- 다음 페이지 없음: `nextPage=null`이면 `더 보기`를 숨긴다.
- 로그인 토큰 없음: 제공처 호출 전에 로그인 필요 상태를 표시한다.

### 요청부터 화면까지의 데이터 흐름

```text
PolicyFilterCondition

  → 앱이 맞춤 추천 / 조건 확인 필요 / 함께 보기 배지와 첫 번째 이유 표시

```

| 응답 상태 | 앱 표시 | 의미 |

| `RECOMMENDED` | 맞춤 추천 | 관심 주제나 현재 상태와 직접 관련된 정책 |

## 19. 추천 기능 3단계 — 개인 정책 브리핑 UX

### 목적

정책 탭을 조건 검색 폼이 아니라 로그인 사용자를 위한 개인 정책 브리핑으로 전환한다. 최초 설정은
필수 정보를 최소화하고, 저장된 조건이 있으면 다시 입력하지 않고 추천 목록을 바로 연다.

### 최종 화면 흐름

```text
최초 이용
  → 1/3 나이·거주 지역
  → 2/3 현재 상황(선택)
  → 3/3 조건 확인·자동 저장
  → 개인 정책 브리핑

재방문
  → 저장 조건 조회
  → 개인 정책 브리핑 바로 표시
```

### 적용한 판단

- 나이는 회원 생년월일에서 가져오고 없을 때만 직접 입력한다.
- 시·도만 필수이며 구·군과 현재 상황은 선택 정보다.
- 정책 분야와 관심 주제는 최초 설정에서 제거한다.
- 로그인 사용자의 조건은 별도 체크박스 없이 계정에 자동 저장한다.
- 추천 목록은 `POST /api/policies/recommendations`를 한 번 호출해 받는다.
- 분야와 정책명은 사용자 프로필이 아니라 현재 목록을 둘러보기 위한 탐색 조건이다.
- `DISCOVER`는 일반 정책으로 표시하고 추천 배지를 노출하지 않는다.
- 지원 금액이 없으면 임의 평균을 만들지 않고 제공처의 실제 지원 내용을 표시한다.

### 목록 구성

1. `내게 잘 맞는 정책`: 첫 추천은 강조 카드, 나머지는 일반 카드
2. `조건을 확인해 볼 정책`: 확인 사유와 함께 표시
3. `더 둘러볼 정책`: 배지 없는 일반 정책

상단에는 조건 요약, 정책명 검색, 전체·분야 칩, 정렬 메뉴를 배치한다. 사용자는 `조건 수정`으로
언제든 3단계 설정에 다시 들어갈 수 있다.

## 20. 추천 기능 4단계 — 홈 정책 브리핑과 신청 마감 구조화

### 목적

사용자가 정책 탭을 직접 열지 않아도 홈에서 저장 조건에 맞는 정책과 곧 마감되는 정책을 발견하게
한다. 신청 기간 원문을 앱이 임의로 해석하지 않고, 백엔드가 안전하게 확인한 종료일만 D-day에
사용한다.

### 요청부터 화면까지의 데이터 흐름

```text
홈 진입
  → GET /api/users/me/policy-preferences
  ├─ 저장 조건 없음 → 홈의 간단 설정 안내 → 정책 탭 이동
  └─ 저장 조건 있음 → POST /api/policies/recommendations (최대 20개)
                     → 맞춤 추천 1건 우선 선택
                     → 30일 이내 마감 정책을 가까운 순서로 보완
                     → 최대 3건의 홈 정책 브리핑 표시
                     → 카드 선택 시 기존 정책 상세 화면 이동
```

### 표시와 새로고침 기준

- 첫 항목은 백엔드의 `RECOMMENDED` 정책을 우선한다.
- 구조화된 `applicationEndDate`가 오늘부터 30일 이내인 정책을 마감 가까운 순으로 보완한다.
- 홈에는 최대 3건만 노출하고 `전체 보기`로 정책 탭에 이동한다.
- 홈 카드는 맞춤 이유, 제공처 지원 내용, 주관 기관을 함께 표시한다.
- 구조화된 지원금이 없으면 평균이나 예상 금액을 만들지 않고 제공처의 지원 내용 원문을 표시한다.
- 탭을 오갈 때마다 외부 정책 API를 다시 호출하지 않는다. 최초 홈 진입과 사용자의 당겨서 새로고침
  때만 정책 브리핑을 갱신한다.
- 저장 조건 조회나 추천 조회가 실패해도 예산·지출 등 다른 홈 기능은 그대로 사용할 수 있다.

### 신청 마감 계약

- 앱은 `applicationPeriodText`에서 날짜를 직접 추출하지 않는다.
- 백엔드가 특정 기간 정책의 정확한 날짜 범위를 확인했을 때만 내려주는
  `applicationEndDate`를 사용한다.
- 종료일이 지났으면 목록에는 `마감`을 표시하고 마감 임박 정렬의 유효 정책 뒤로 보낸다.
- 상시, 이미 마감으로 분류된 정책, 설명이 섞인 기간, 잘못된 날짜는 원문만 표시한다.

### 완료 상태

- [x] 홈 저장 조건 확인과 추천 API 재사용
- [x] 맞춤 추천·30일 이내 마감 정책 최대 3건 선별
- [x] 홈 카드의 추천 이유·지원 내용·D-day 표시
- [x] 홈 카드 상세 이동과 전체 정책 탭 이동
- [x] 저장 조건 없음·빈 결과·부분 실패 화면
- [x] 정책 목록 마감 정렬을 구조화된 종료일 기준으로 전환
- [x] 홈 브리핑과 기존 정책 흐름 자동 테스트
- [ ] 실제 서버·앱에서 홈 브리핑 수동 확인

다음 디테일 단계에서는 실제 제공처 결과를 보며 추천 이유 문구와 카드 정보 밀도를 조정한다.
이 단계에서는 구조화 금액이 없어 제공처 원문만 표시했다. 이후 24단계에서도 평균·예상 총액은
만들지 않고, 백엔드가 확실한 근거로 구조화한 금액만 표시한다.

## 21. 정책 디테일 1단계 — 상세 정보 구조와 숨기기 흐름 정리

### 목적

정책 상세에서 지원 내용과 신청 기간이 여러 카드에 반복되고, 사용자가 실제로 해야 할 행동이 화면
아래에 흩어져 있던 문제를 정리한다. 추천 이유부터 신청 준비까지 읽는 순서를 명확히 하고, 기존에
안내 문구만 표시하던 상세 화면의 숨기기 버튼을 실제 홈·정책 목록 상태에 반영한다.

### 상세 화면 정보 순서

```text
정책명·분야·설명
  → 나에게 맞는 이유 또는 신청 전 확인 조건
  → 한눈에 보기(지원 혜택·신청 기간·지원 대상)
  → 신청 준비(신청 방법·제출 서류)
  → 담당 기관(주관·운영)
  → 참고 링크
  → 목록에서 숨기기 / 신청 사이트 확인
```

### 적용한 판단

- 구조화 금액이 있으면 `지원 금액`, 없으면 제공처 원문을 `지원 혜택`으로 표시한다.
- `예상 지원액`이라는 표현을 제거해 제공처 원문이 예상 총액처럼 보이지 않게 한다.
- 신청 종료일이 있으면 상세 화면에도 `D-day`, `오늘 마감`, `접수 마감` 상태를 표시한다.
- 신청 주소가 기관 홈페이지나 로그인 화면일 수 있으므로 버튼은 `신청 사이트 확인`으로 표현한다.
- 지원 내용·대상·기간을 각각 별도 카드로 반복하지 않고 `한눈에 보기` 카드로 묶는다.
- 신청 방법과 제출 서류는 실제 행동 순서에 맞게 `신청 준비` 카드로 묶는다.
- 주관 기관과 운영 기관은 `담당 기관` 카드 한 곳에서 비교할 수 있게 한다.

### 숨기기 데이터 흐름

```text
홈 또는 정책 목록 → 정책 상세
  → 목록에서 숨기기
  → PolicyDetailAction.hide 반환
  ├─ 정책 목록 진입 → 해당 목록에서 제거 → 실행취소 가능
  └─ 홈 진입 → 홈 브리핑에서 제거 → 실행취소 가능
```

이번 숨기기는 기존 정책 목록과 동일한 화면 메모리 상태다. 앱 재실행 후에도 숨김을 유지하려면
사용자별 숨김 정책 저장 구조, 해제 정책, 탈퇴 시 삭제 범위를 먼저 합의한 뒤 백엔드 영속화를
별도 단계로 구현한다.

### 완료 상태

- [x] 정책 상세 정보 계층 재구성
- [x] 추천·확인 필요 이유를 항목별로 표시
- [x] 지원 금액과 제공처 지원 원문의 중복 제거
- [x] 구조화 종료일 기반 상세 마감 상태 표시
- [x] 신청 방법·제출 서류와 담당 기관 묶음 구성
- [x] 신청 버튼의 실제 링크 성격을 반영한 문구 변경
- [x] 상세 숨기기의 홈·정책 목록 반영과 실행취소
- [x] 상세 이동·마감·숨기기 위젯 테스트
- [ ] 사용자의 실제 앱 화면 수동 확인

다음 디테일 단계에서는 실제 화면 확인 결과를 바탕으로 홈·목록 카드의 높이와 표시 문구를
미세 조정한다. 숨김 영속화는 DB와 삭제 정책 판단이 필요한 별도 단계로 남긴다.

## 22. 정책 안정화 — 소셜 계정 추천과 상세 조회 실패 보완

### 해결한 문제

- 소셜 제공처에서 생년월일을 받지 못한 계정은 정책 화면에서 나이를 입력해도 서버 저장 요청에서
  나이가 빠져 추천 API가 기본 조건 없음으로 거절하던 문제를 수정한다.
- 목록 카드를 선택한 뒤 외부 상세 API가 지연되거나 실패하면 상세 정보 전체가 사라지던 문제를
  목록 응답 폴백으로 보완한다.
- 실제 앱 라우터는 `dynamic` 결과 라우트를 사용하지만 상세 호출부만 전용 결과 타입을 요구해
  화면 전환 전에 런타임 타입 오류가 발생하던 문제를 실제 라우터 계약에 맞춘다.

### 데이터 흐름

```text
소셜 로그인 사용자 → 정책 조건에서 현재 만 나이 입력
  → PUT /api/users/me/policy-preferences에 age 포함
  → 회원 생년월일이 없을 때 저장 age를 추천 조건으로 사용
  → 다음 로그인에서도 저장 조건과 추천 목록 복원

정책 카드 선택 → 목록의 PolicySummary를 상세 인자로 전달
  → 상세 화면을 기본 정보로 즉시 표시
  → GET /api/policies/{policyId} 성공 시 전체 상세로 갱신
  └─ 실패 시 기본 정보를 유지하고 다시 시도 제공
```

### 확인 항목

- [x] 정책 조건 저장 요청에 `age` 포함
- [x] 홈과 정책 목록에서 상세 폴백 정보 전달
- [x] 상세 API 로딩·실패 중 기본 상세 화면 유지
- [x] 상세 재시도 제공
- [x] 홈·정책 목록의 상세 라우트 결과 타입을 실제 앱 라우터와 통일
- [x] 요청 계약과 상세 폴백 위젯 테스트 추가
- [ ] 카카오·네이버 생년월일 미제공 계정 수동 확인

## 23. 정책 디테일 2단계 — 홈·목록 카드 안정화와 디자인 마감

### 목적

실제 제공처 정책명, 지원 내용, 신청 기간과 기관명은 길이가 일정하지 않다. 작은 Android 화면에서도
정보가 서로 밀어내거나 잘리지 않도록 카드의 정보 순서를 정리하고, 사용자가 카드 전체를 상세 화면
진입 요소로 이해할 수 있게 접근성을 보완한다. 이 단계는 앱 표시만 변경하며 API 요청·응답과 DB
계약은 변경하지 않는다.

### 적용한 표시 기준

- 홈 카드는 추천 상태·마감·분야를 먼저 보여주고 정책명, 추천 이유, 지원 내용, 담당 기관 순서로 읽는다.
- 정책 목록의 대표 카드는 추천 이유를 별도 강조 영역에 표시한다.
- 일반 목록 카드는 지원 내용과 분야·신청 기간을 서로 다른 줄에 배치해 가로 공간 경쟁을 줄인다.
- 정책명·지원 내용·추천 이유·기관명에는 화면 역할에 맞는 최대 줄 수와 말줄임을 적용한다.
- 긴 분야와 신청 기간은 제한된 너비 안에서 말줄임 처리하고, 숨기기 메뉴는 44×44 터치 영역을 확보한다.
- 전체 카드는 정책명을 포함한 상세 보기 버튼 의미를 스크린 리더에 제공한다.
- 오류와 로딩 문구는 작은 화면에서도 재시도 버튼이나 아이콘과 겹치지 않는 세로 구조를 사용한다.

### 완료 상태

- [x] 홈 정책 카드 정보 계층과 상세 이동 표현 정리
- [x] 정책 목록 대표·일반 카드의 긴 문구 처리
- [x] 분야·기관·신청 기간의 작은 화면 배치 보완
- [x] 정책 카드와 숨기기 메뉴의 접근성 의미·터치 영역 보완
- [x] 홈·목록 오류와 로딩 상태의 긴 문구 대응
- [x] 320×568 화면과 긴 제공처 데이터를 사용하는 위젯 테스트 추가
- [ ] 사용자의 Android 실기기 화면 수동 확인

다음 단계에서는 실기기 확인 결과를 반영한 간격 조정만 수행한다. 지원금 구조화, 외부 링크 품질과
관심 없음 영속화는 각각 데이터 정확도와 DB 저장 정책 판단이 필요한 후속 단계로 유지한다.

## 24. 정책 디테일 3단계 — 근거 기반 금액·기간·링크 안내

### 목적

제공처 설명에서 확실하게 확인되는 정보만 구조화해 목록과 상세의 핵심 정보를 빠르게 읽을 수 있게
한다. 평균·예상 총액을 만들지 않고, 백엔드가 함께 반환하는 유형으로 금액의 기준과 링크의 성격을
명확히 안내한다. 기존 서버 응답에도 앱이 동작하도록 새 필드는 선택적으로 해석한다.

### 요청부터 화면까지의 데이터 흐름

```text
온통청년 지원 내용·신청 기간·URL 원문
  → 백엔드가 확실한 값만 금액·기간·링크 유형으로 구조화
  → 정책 목록·홈이 월/최대 금액과 기간 상태를 짧은 라벨로 표시
  → 정책 상세가 원문과 구조화 라벨을 함께 표시
  → 신청 링크 확인 화면이 로그인·기관 홈페이지·신청 후보를 구분해 안내
```

### 표시 기준

- `FIXED`, `MAXIMUM`, `MONTHLY`, `MONTHLY_MAXIMUM`에 따라 `50만원`, `최대 50만원`,
  `월 50만원`, `월 최대 50만원`으로 표시한다.
- 구조화 금액이 없으면 기존처럼 제공처의 지원 내용 원문을 표시한다.
- 지원 금액 정렬은 총액성 금액과 월 금액을 서로 직접 비교하지 않고 각각의 유형 묶음 안에서
  큰 금액 순으로 정렬한다.
- `ALWAYS`, `CLOSED`, `UNTIL_BUDGET`은 각각 `상시 신청`, `접수 마감`,
  `예산 소진 시까지`로 표시한다.
- 정확한 날짜 범위는 백엔드가 제공한 시작일·종료일만 사용하며 앱이 원문에서 다시 추측하지 않는다.
- 신청 후보 URL은 `신청 페이지 확인`, 로그인 URL은 `로그인 후 신청 확인`, 기관 루트 URL은
  `기관 홈페이지 확인`으로 구분한다.
- 로그인 유형의 확인 화면은 `로그인이 필요한 서비스입니다`를 먼저 알리고 외부 서비스에서 로그인을
  이어 가도록 안내한다.
- 기관 홈페이지 유형은 바로 신청 화면이라고 단정하지 않고 정책명 검색이 필요할 수 있음을 알린다.
- 새 유형 필드가 없는 구버전 서버 응답은 기존 URL·원문 표시로 안전하게 되돌아간다.

### 실패와 호환 처리

- 알 수 없는 금액 유형은 금액 숫자만 표시하고 앱 응답 파싱을 실패시키지 않는다.
- 알 수 없는 기간 유형은 제공처 신청 기간 원문을 표시한다.
- URL이 비어 있으면 신청 버튼을 비활성화하고 `신청 링크 없음`을 표시한다.
- 링크 유형은 접속 성공을 보장하지 않으므로 외부 페이지 오류나 변경 가능성은 남아 있다.
- DB와 사용자 저장 구조는 변경하지 않는다.

- [x] 목록·홈·상세의 유형별 금액과 기간 라벨
- [x] 링크 품질별 상세 버튼과 외부 이동 전 안내

## 25. 정책 디테일 4단계 — 목록 핵심 문구와 상세 표기 정돈

### 목적

제공처가 내려주는 지원 내용과 상세 설명은 길이와 글머리 기호가 일정하지 않다. 목록에서는 전체
원문 때문에 카드의 핵심을 빠르게 파악하기 어렵고, 상세에서는 동그라미·네모·점이 섞여 보이는
문제를 앱 표시 단계에서 정돈한다. API 원문과 응답 계약은 변경하지 않는다.

### 적용 기준

- 목록과 홈 정책 카드는 구조화 금액이 있으면 기존 금액 라벨을 우선 표시한다.
- 구조화 금액이 없으면 지원 내용의 첫 번째 유효 문장만 사용하고 최대 52자로 제한한다.
- 지원 내용이 없으면 정책 요약을 같은 기준으로 사용하고, 둘 다 없을 때만 `지원 내용 확인`을 표시한다.
- 상세 원문의 `○`, `●`, `□`, `■`, `▪`, `▶`, `※`, `-`, `*` 등은 화면에서 `•`로 통일한다.
- 추천 이유와 제출 서류 목록은 같은 작은 원형 불릿과 간격을 사용한다.
- 원문 데이터는 수정하지 않아 상세 정보 누락이나 API 계약 변경이 발생하지 않게 한다.
- 현재 상황 선택 버튼은 2열 동일 너비와 52 높이로 맞추고 선택 체크 표시로 인한 크기 변화도 막는다.
- 하단 `이전`과 `다음` 버튼도 같은 52 높이를 명시한다.

### 데이터 흐름

```text
PolicySummary.supportText / summary
  → 목록 표시용 글머리 제거와 첫 문장 추출
  → 최대 52자 핵심 문구
  → 정책 목록·홈 카드 표시

PolicyDetail 원문
  → 화면 전용 텍스트 정돈
  → 혼합 글머리 기호를 단일 원형 불릿으로 변환
  → 상세 설명·혜택·기간·대상·신청 준비 표시
```

### 완료 상태

- [x] 목록과 홈 카드의 긴 지원 원문을 핵심 문장으로 축약
- [x] 상세 원문의 혼합 글머리 기호 통일
- [x] 추천 이유와 제출 서류 불릿 디자인 통일
- [x] 현재 상황 선택 버튼의 너비·높이 정렬
- [x] 조건 설정 하단 이동 버튼 높이 정렬
- [ ] 사용자의 Android 실기기 화면 수동 확인

다음 검토에서는 재직·구직 조건이 추천 순위에 실제로 어떤 차이를 만드는지 백엔드 추천 평가 흐름을
확인한다. 이 단계에서는 추천 알고리즘이나 API 계약을 변경하지 않는다.

## 26. 정책 디테일 5단계 — 구조화된 한 줄 핵심 요약

### 목적

목록에서 상세 원문의 첫 줄을 잘라 보여주는 대신 정책 전체 내용에서 지원 주제를 분석한 짧고
기호 없는 문장을 표시한다. 앱과 추후 웹이 같은 문장을 사용하도록 요약 생성은 백엔드에서 한 번만
수행한다.

### 선택한 방식과 이유

- AI를 호출하지 않고 정책명·설명·중분류·키워드·지원 내용 전체를 규칙으로 분류한다.
- 월세·교통·자격증·창업·취업·교육·문화·자산 형성·건강·생활·주거·참여 주제를 구분한다.
- 확실하게 구조화된 지원금이 있으면 주제와 금액 유형을 한 문장으로 조합한다.
- 평균이나 예상 금액은 만들지 않고 기존 구조화 금액만 사용한다.
- 백엔드가 선택적인 `shortSummary`를 반환해 구버전 서버에서도 앱이 계속 동작하게 한다.

### 요청부터 화면까지의 데이터 흐름

```text
온통청년 정책명·설명·분류·키워드·지원 내용
  → 백엔드가 전체 텍스트에서 지원 주제 분류
  → 구조화 금액이 있으면 월·최대 유형과 함께 문장 조합
  → shortSummary 반환
  → 앱 목록·홈 카드가 한 줄로 표시
  → shortSummary 누락 시 기존 금액 또는 첫 핵심 문장으로 하위 호환
```

### 표시 예시

```text
청년의 월세와 주거비를 월 최대 20만원 지원해요
청년의 취업과 일자리 준비를 지원해요
청년의 문화와 예술 활동 참여를 지원해요
```

- [x] 정책 목록과 홈 카드에서 구조화 요약 우선 표시
- [x] 대표 요약과 추천 이유를 한 줄로 제한
- [x] 구조화 요약 누락 시 기존 표시 규칙 유지
- [x] API 파싱·정책 목록·홈 브리핑 검증 사례 추가
